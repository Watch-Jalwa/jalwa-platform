# Self-hosted staging environment contract

Status: authoritative staging infrastructure contract for Jalwa. The application release is merged and CI-certified; live staging execution is blocked until the protected GitHub `staging` environment is populated with the owner-controlled host and external-service values below.

## Target architecture

Jalwa staging runs on an owner-controlled Linux server over SSH using the repository's Docker/Compose deployment tooling.

- Jalwa web/PWA, server routes and Better Auth run in the web container.
- Jalwa background/media work runs in the worker container.
- PostgreSQL is the source-of-truth database and is accessed directly by the application/worker.
- Better Auth persists directly to PostgreSQL and sends magic links through SMTP.
- Caddy exposes the customer site; application API/Auth routes remain under the customer domain.
- Cloudflare R2 plus FFmpeg is the initial staging media path, with the media gateway at `media.<staging-domain>`.
- GitHub Actions builds immutable GHCR images and deploys them to the configured SSH host.
- There is no Supabase Auth/REST/API runtime gateway.
- Production is never deployed automatically by staging certification.

The deployment host may be any suitable owner-controlled Linux server. Vercel is not required and DigitalOcean provisioning is optional.

## Server prerequisites

Prepare the host with:

- a supported Linux distribution with current security updates;
- Docker Engine and Docker Compose;
- a dedicated non-root deployment user, default `jalwa`;
- SSH key authentication and an independently verified host key;
- persistent PostgreSQL storage and `/opt/jalwa/backups`;
- inbound 80/443 and restricted SSH access;
- DNS-ready public addresses for the staging site and media subdomain;
- `/opt/jalwa/{scripts,systemd,migrations,backups/postgres,operations,secrets,deployments}` with deployment-user ownership;
- sufficient disk/RAM for web, worker, PostgreSQL and FFmpeg work.

Do not put real secret values in repository files, issues, chat or messaging apps.

## Values generated or owned by Jalwa/DevOps

These values can be generated during staging setup, but they still require a real owner-controlled host before deployment can proceed.

### GitHub `staging` variables

- `STAGING_HOST` — server hostname or IP reachable from GitHub Actions.
- `STAGING_USER` — deployment user; defaults to `jalwa`.
- `STAGING_SSH_KNOWN_HOSTS` — independently verified SSH host-key entry containing `STAGING_HOST`.
- `SMTP_PORT` — defaults to `587` when appropriate.
- `SMTP_SECURE` — defaults to `false` when appropriate.
- `STAGING_QA_ALLOWED_EMAILS` — optional allowlist for protected QA endpoints.

### GitHub `staging` secrets generated by Jalwa/DevOps

- `STAGING_SSH_KEY`
- `SELF_HOSTED_POSTGRES_PASSWORD`
- `BETTER_AUTH_SECRET` — at least 32 characters.
- `STAGING_QA_SECRET` — at least 32 characters.
- `BACKUP_AGE_IDENTITY` — age X25519 identity beginning with `AGE-SECRET-KEY-`.
- `MEDIA_SIGNING_SECRET`
- `RATE_LIMIT_SALT`
- `OBSERVABILITY_HASH_SALT`
- `RECOMMENDATION_REFRESH_SECRET`
- `CRON_SECRET`
- `ACCOUNT_REQUEST_PROCESSOR_SECRET`
- `ACCOUNT_DELETION_HASH_SECRET`
- `OPERATIONS_DIAGNOSTICS_SECRET`
- `PAYMENT_WEBHOOK_SECRET` for the isolated mock staging provider.

Generated secrets must be stored only in the protected GitHub `staging` environment or the staging host secret store; do not commit them.

If an external mailbox API is later required to prove physical inbox delivery, its credentials must be added as a separate protected integration.

## Ordinary staging variables

Configure these as GitHub `staging` environment variables, not secrets:

- `R2_INCOMING_BUCKET` — must use a `jalwa-staging-...` name.
- `R2_PROCESSED_BUCKET` — must use a `jalwa-staging-...` name.
- `R2_BACKUP_BUCKET` — must use a `jalwa-staging-...` name.
- `MINIMUM_STAGING_CONTENT_ITEMS`
- `STAGING_EXPECT_PUBLIC_DOMAIN_LIVE_SOURCES` — normally `false` until approved.
- `STAGING_VISUAL_REVIEW_ACCEPTED` — empty until a visual difference is explicitly approved; an approval must be the exact 40-character release SHA, never `true`.
- `STAGING_VISUAL_REVIEW_ACCEPTANCE_REFERENCE` — human review reference for that exact SHA.

Runtime values are derived from the protected staging inputs:

- `APP_URL=https://<STAGING_DOMAIN>`
- `NEXT_PUBLIC_APP_URL=https://<STAGING_DOMAIN>`
- `BETTER_AUTH_URL=https://<STAGING_DOMAIN>`
- `DATABASE_URL=postgresql://postgres:<SELF_HOSTED_POSTGRES_PASSWORD>@postgres:5432/postgres`
- `NEXT_PUBLIC_MEDIA_GATEWAY_URL=https://media.<STAGING_DOMAIN>`

## Fixed staging safety settings

The deployment workflow keeps these controls until a later explicitly approved phase:

- `DEPLOYMENT_ENVIRONMENT=staging`
- `PAYMENT_PROVIDER=mock`
- `ALLOW_MOCK_PAYMENTS=true`
- real payment credentials disabled;
- public-domain live sources disabled unless explicitly enabled for staging certification;
- live streaming disabled;
- web DRM disabled;
- staging `noindex` enabled;
- production credentials/resources isolated from staging.

## Deployment and certification sequence

1. Prepare the SSH/Docker host and DNS/TLS.
2. Add all required protected values to the GitHub `staging` environment.
3. Run **Deploy staging** from the exact green `main` SHA.
4. The workflow builds immutable web/worker GHCR images, deploys the Cloudflare media gateway, writes the direct PostgreSQL/Better Auth runtime environment, applies migrations, deploys transactionally, captures source-to-running-artifact identity, takes backups and performs the restore drill.
5. **Staging certification** runs automatically for the successful deployment SHA.
6. Mandatory Playwright/runtime areas run against the real customer site/Auth/API and produce retained sanitized evidence.
7. Missing required infrastructure/fixtures is `BLOCKED`; reproducible product defects are `FAILED`.
8. Visual differences require explicit human review tied to the exact release SHA.
9. Only `READY FOR UAT` permits human UAT.
10. Production remains a separate explicit approval and must promote the exact tested immutable artifacts; it must not rebuild an untested release.

## Current infrastructure blocker

The first real `Deploy staging` validation run found the protected `staging` environment unconfigured: `STAGING_HOST`, `STAGING_DOMAIN`, SSH/GHCR, Cloudflare/R2, SMTP and the required Jalwa staging secrets/variables were empty. Until the owner-controlled host/domain and external-service credentials exist, live deployment and certification cannot truthfully proceed.

## Production handoff prepared in advance

Before any production approval, retain:

- exact staging-tested Git SHA;
- web/worker GHCR image digests;
- successful staging certification artifact;
- human UAT approval;
- pre-production backup/restore evidence;
- tested rollback reference.

After explicit production approval, deploy only the exact tested artifacts to the owner-controlled production server, run non-destructive smoke/health checks, keep rollback immediately available, and retire any prior production environment only after the new environment is verified healthy.
