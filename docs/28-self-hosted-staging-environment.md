# Self-hosted staging environment contract

Status: authoritative staging infrastructure contract for Jalwa. Vercel and DigitalOcean provisioning are not part of the required release path.

## Target architecture

Jalwa staging runs on an owner-controlled Linux server over SSH using the repository's Docker/Compose deployment tooling.

- Jalwa web/PWA and server routes run in the web container.
- Jalwa background/media work runs in the worker container.
- PostgreSQL is the source-of-truth database.
- Self-hosted Supabase provides Auth and REST/API services around that PostgreSQL database.
- Caddy/reverse-proxy routing exposes the customer site and `api.<staging-domain>`.
- Cloudflare R2 plus FFmpeg remains the initial staging media path.
- GitHub Actions builds immutable GHCR images and deploys them to the configured SSH host.
- Production is never deployed automatically by staging certification.

The deployment host may be any suitable owner-controlled server. The repository does not require Vercel and does not require DigitalOcean provisioning.

## Server prerequisites that DevOps can complete before project credentials arrive

Prepare the host with:

- a supported Linux distribution with current security updates;
- Docker Engine and Docker Compose;
- a dedicated non-root deployment user, default `jalwa`;
- SSH key authentication and an independently verified host key;
- persistent storage for PostgreSQL/Supabase and `/opt/jalwa/backups`;
- inbound 80/443 and restricted SSH access;
- DNS-ready public addresses for the staging site and API;
- `/opt/jalwa/{scripts,systemd,migrations,supabase,backups/postgres,operations,secrets,deployments}` with deployment-user ownership;
- sufficient disk/RAM for web, worker, PostgreSQL, Supabase Auth/REST and FFmpeg work.

Do not put real secret values in repository files, issues, chat or WhatsApp.

## Ordinary staging variables

Configure these as GitHub `staging` environment variables, not secrets:

- `R2_INCOMING_BUCKET` — must use `jalwa-staging-...`.
- `R2_PROCESSED_BUCKET` — must use `jalwa-staging-...`.
- `R2_BACKUP_BUCKET` — must use `jalwa-staging-...`.
- `MINIMUM_STAGING_CONTENT_ITEMS`
- `STAGING_EXPECT_PUBLIC_DOMAIN_LIVE_SOURCES` — normally `false` until approved.
- `STAGING_VISUAL_REVIEW_ACCEPTED` — empty until a visual difference is explicitly approved; approval value must be the exact 40-character release SHA, never `true`.
- `STAGING_VISUAL_REVIEW_ACCEPTANCE_REFERENCE` — human review reference for that exact SHA.

Runtime URLs are derived from `STAGING_DOMAIN`; they are not independent secrets:

- `NEXT_PUBLIC_APP_URL=https://<STAGING_DOMAIN>`
- `NEXT_PUBLIC_SUPABASE_URL=https://api.<STAGING_DOMAIN>`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<SELF_HOSTED_SUPABASE_ANON_KEY>`
- `SUPABASE_SERVICE_ROLE_KEY=<SELF_HOSTED_SUPABASE_SERVICE_ROLE_KEY>`
- `DATABASE_URL=postgresql://postgres:<SELF_HOSTED_POSTGRES_PASSWORD>@supabase-db:5432/postgres`
- `AUTH_REDIRECT_URL=https://<STAGING_DOMAIN>/auth/callback`
- `NEXT_PUBLIC_MEDIA_GATEWAY_URL=https://media.<STAGING_DOMAIN>`

## Fixed staging safety settings

The deployment workflow must keep these controls until a later explicitly approved phase:

- `DEPLOYMENT_ENVIRONMENT=staging`
- `PAYMENT_PROVIDER=mock`
- `ALLOW_MOCK_PAYMENTS=true`
- real payment credentials disabled;
- live streaming disabled;
- web DRM disabled;
- staging `noindex` enabled;
- production credentials/resources isolated from staging.

## Deployment and certification sequence

1. DevOps prepares the generic SSH/Docker host and DNS/TLS.
2. Required protected values are added to the GitHub `staging` environment.
3. Merge the reviewed release-quality PR only after repository checks and owner approval.
4. Run **Deploy staging** from the exact green `main` SHA.
5. The workflow builds immutable web/worker GHCR images, writes runtime environments, prepares self-hosted Supabase/PostgreSQL, applies migrations, deploys transactionally, captures source-to-running-artifact identity, takes backups and performs a restore drill.
6. **Staging certification** runs against that exact deployed SHA.
7. Mandatory Playwright areas run against the real customer site/Auth/API and produce retained reports. Missing required infrastructure/fixtures are `BLOCKED`; reproducible product defects are `FAILED`.
8. Visual differences require explicit human review tied to the exact release SHA.
9. Only `READY FOR UAT` permits human UAT.
10. Production remains a separate explicit approval and must promote the exact tested immutable artifacts; it must not rebuild an untested release.

## Production handoff prepared in advance

Before any production approval, retain:

- exact staging-tested Git SHA;
- web/worker GHCR image digests;
- successful staging certification artifact;
- human UAT approval;
- pre-production backup/restore evidence;
- tested rollback reference.

After explicit production approval, deploy the exact tested artifacts to the owner-controlled production server, run non-destructive smoke/health checks, keep rollback immediately available, and retire the old production environment only after the new environment is verified healthy.
