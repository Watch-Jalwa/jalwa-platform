# Self-hosted staging environment contract

Status: authoritative staging infrastructure contract for Jalwa. Repository-owned bootstrap/deploy logic is automated; live staging execution still requires the protected GitHub `staging` environment to contain the owner-controlled external-service credentials listed below.

## Target architecture

Jalwa staging runs on an owner-controlled Linux server over SSH using the repository's Docker/Compose deployment tooling.

- Jalwa web/PWA, server routes and Better Auth run in the web container.
- Jalwa background/media work runs in the worker container.
- PostgreSQL is the source-of-truth database and is accessed directly by the application/worker.
- Better Auth persists directly to PostgreSQL and sends magic links through SMTP.
- Caddy exposes the customer site; application API/Auth routes remain under the customer domain.
- Cloudflare R2 plus FFmpeg is the initial staging media path, with the media gateway at `media.<staging-domain>`.
- GitHub Actions builds immutable GHCR images and deploys them to the configured SSH host.
- There is no Supabase Auth/REST/API runtime gateway.
- Production is never deployed automatically by staging certification.

The provided bootstrap provisions DigitalOcean. Another owner-controlled Linux host may be used only if the same deployment/firewall contract is implemented separately.

## SSH/firewall model

By default the DigitalOcean firewall has no persistent SSH source at all. The optional bootstrap input `admin_cidr` may be supplied when a deliberately controlled break-glass office/VPN/public IPv4 CIDR should retain SSH access; if it is empty, no persistent TCP/22 rule is created.

For bootstrap and deployment, the workflow discovers the current runner's public IPv4 address, adds one temporary TCP/22 `/32` rule through the DigitalOcean firewall Rules API, performs the required pinned-host-key SSH/scp operation, and removes the rule on exit, including command failure. The bootstrap persists the firewall ID as `STAGING_FIREWALL_ID` so later deployments can repeat that narrow access grant. The DigitalOcean token therefore requires the firewall update scope in addition to the scopes required for provisioning.

## Server prerequisites

Prepare the host with:

- a supported Linux distribution with current security updates;
- Docker Engine and Docker Compose;
- a dedicated non-root deployment user, default `jalwa`;
- SSH key authentication and an independently verified host key;
- persistent PostgreSQL storage and `/opt/jalwa/backups`;
- inbound 80/443 and temporary deployment-runner SSH access, plus optional deliberate break-glass SSH access;
- DNS-ready public addresses for the staging site and media subdomain;
- `/opt/jalwa/{scripts,systemd,migrations,backups/postgres,operations,secrets,deployments}` with deployment-user ownership;
- sufficient disk/RAM for web, worker, PostgreSQL and FFmpeg work.

Do not put real secret values in repository files, issues, chat or messaging apps.

## Values generated by bootstrap

The staging bootstrap generates only missing Jalwa-owned secrets. Existing secret names are inspected first; an existing SSH private key that is not exposed to the job is treated as a fail-closed condition rather than silently rotated.

### GitHub `staging` variables generated/persisted by bootstrap

- `STAGING_HOST` — provisioned server IPv4/hostname.
- `STAGING_FIREWALL_ID` — DigitalOcean firewall used for temporary GitHub-runner SSH access.
- `STAGING_USER` — deployment user; defaults to `jalwa`.
- `STAGING_DOMAIN` — selected bootstrap domain.
- `STAGING_SSH_KNOWN_HOSTS` — pinned Ed25519 host-key entry captured while the runner has temporary `/32` access.
- `R2_INCOMING_BUCKET` — `jalwa-staging-incoming`.
- `R2_PROCESSED_BUCKET` — `jalwa-staging-media`.
- `R2_BACKUP_BUCKET` — `jalwa-staging-backups`.

### GitHub `staging` secrets generated only when absent

- `STAGING_SSH_KEY`
- `SELF_HOSTED_POSTGRES_PASSWORD`
- `BETTER_AUTH_SECRET` — at least 32 characters.
- `STAGING_QA_SECRET` — at least 32 characters.
- `BACKUP_AGE_IDENTITY` — age X25519 identity beginning with `AGE-SECRET-KEY-`.
- `MEDIA_SIGNING_SECRET`
- `RATE_LIMIT_SALT`
- `OBSERVABILITY_HASH_SALT`
- `RECOMMENDATION_REFRESH_SECRET`
- `CRON_SECRET`
- `ACCOUNT_REQUEST_PROCESSOR_SECRET`
- `ACCOUNT_DELETION_HASH_SECRET`
- `OPERATIONS_DIAGNOSTICS_SECRET`
- `PAYMENT_WEBHOOK_SECRET` for the isolated mock staging provider.

Generated secrets must remain in the protected GitHub `staging` environment or the staging host secret store; do not commit them.

### Payment-service/JazzCash staging values

These are external account-owned inputs and are used only by the protected **Payment service staging preflight** and later payment UAT. They are not generated by Jalwa and must not be committed:

GitHub `staging` variables:

- `STAGING_PAYMENT_SERVICE_BASE_URL` — HTTPS staging payment-service origin.
- `STAGING_PAYMENT_SERVICE_EXPECTED_PORTAL_HOST` — expected JazzCash sandbox/hosted portal hostname returned by wallet-link initiation.

GitHub `staging` secrets:

- `STAGING_PAYMENT_SERVICE_API_KEY` — product API key sent only by the Jalwa server as `X-Api-Key`.
- `STAGING_PAYMENT_SERVICE_WEBHOOK_SECRET` — product webhook HMAC secret.
- `STAGING_PAYMENT_SERVICE_TEST_MSISDN` — dedicated 11–15 digit staging/sandbox JazzCash number; it must not be a production customer number.

The payment-service product itself must also be configured with:

- product webhook URL `https://<STAGING_DOMAIN>/api/webhooks/payment-service`;
- the same webhook secret as `STAGING_PAYMENT_SERVICE_WEBHOOK_SECRET`;
- the product API key corresponding to `STAGING_PAYMENT_SERVICE_API_KEY`;
- Jalwa's staging origin in the payment service wallet-app-return allowlist;
- a supported JazzCash/payment-service sandbox mechanism for any UAT step that completes the hosted wallet/MPIN flow.

The repository does not invent a JazzCash MPIN, provider token, sandbox account or undocumented simulator endpoint.

The bootstrap workflow input `admin_cidr` is optional. Leave it empty for deployment-runner-only SSH, or provide a deliberately controlled IPv4 CIDR for persistent break-glass access.

`GHCR_USERNAME` and `GHCR_DEPLOY_TOKEN` are **not** required. Staging builds and remote image pulls use the workflow's run-scoped GitHub identity/token, and the remote host logs out of GHCR after the deployment operation.

### QA identity values

The suite uses Better Auth magic-link identities and protected staging-only QA endpoints; no QA passwords belong in source control. The following may be supplied as synthetic inboxes/test identities or left at repository defaults when those addresses are routable:

- `STAGING_QA_CUSTOMER_EMAIL`
- `STAGING_QA_ADMIN_EMAIL`
- `STAGING_QA_RESTRICTED_EMAIL`
- `STAGING_QA_UNAUTHORIZED_EMAIL`
- `STAGING_QA_FINANCE_EMAIL`
- `STAGING_QA_REPORT_VIEWER_EMAIL`

If an external mailbox API is later required to prove physical inbox delivery, its credentials must be added as a separate protected integration.

## Ordinary staging variables

Configure these as GitHub `staging` environment variables when needed:

- `SMTP_PORT` — defaults to `587`.
- `SMTP_SECURE` — defaults to `false`.
- `STAGING_QA_ALLOWED_EMAILS` — optional protected-QA allowlist.
- `MINIMUM_STAGING_CONTENT_ITEMS`
- `STAGING_EXPECT_PUBLIC_DOMAIN_LIVE_SOURCES` — normally `false` until approved.
- `STAGING_VISUAL_REVIEW_ACCEPTED` — empty until a visual difference is explicitly approved; an approval must be the exact 40-character release SHA, never `true`.
- `STAGING_VISUAL_REVIEW_ACCEPTANCE_REFERENCE` — human review reference for that exact SHA.

Runtime values are derived from the protected staging inputs:

- `APP_URL=https://<STAGING_DOMAIN>`
- `NEXT_PUBLIC_APP_URL=https://<STAGING_DOMAIN>`
- `BETTER_AUTH_URL=https://<STAGING_DOMAIN>`
- `DATABASE_URL=postgresql://postgres:<SELF_HOSTED_POSTGRES_PASSWORD>@postgres:5432/postgres`
- `NEXT_PUBLIC_MEDIA_GATEWAY_URL=https://media.<STAGING_DOMAIN>`

## Fixed staging safety settings

The ordinary deployment workflow keeps these controls until a later explicitly approved phase:

- `DEPLOYMENT_ENVIRONMENT=staging`
- `PAYMENT_PROVIDER=mock`
- `ALLOW_MOCK_PAYMENTS=true`
- the payment-service wallet integration is not part of the ordinary persistent staging runtime;
- real payment credentials disabled in ordinary staging deployment;
- public-domain live sources disabled unless explicitly enabled for staging certification;
- live streaming disabled;
- web DRM disabled;
- staging `noindex` enabled;
- production credentials/resources isolated from staging;
- persistent SSH is absent by default; optional `admin_cidr` is break-glass only; GitHub runner access is temporary per operation.

The dedicated **Payment service staging preflight** is the only automated workflow allowed to temporarily enable `PAYMENT_SERVICE_ENABLED=true` on the exact deployed staging images. It injects protected server-only payment-service values for the test window, sets mock charging off for that window, runs the authenticated boundary tests, then restores the prior staging environment and recreates the web container even when the preflight fails. A preflight never authorizes production charging.

## Deployment and certification sequence

1. Put the external account credentials and `GITHUB_ENV_ADMIN_TOKEN` in the protected GitHub `staging` environment.
2. Dispatch **Bootstrap staging**; leave `admin_cidr` empty for deployment-runner-only SSH or provide a controlled break-glass CIDR. The workflow generates missing Jalwa-owned secrets, creates isolated R2 buckets, provisions `jalwa-staging`, captures the pinned SSH identity using temporary runner `/32` access, configures DNS and persists host/firewall/bucket outputs.
3. Configure SMTP/DeepSeek values and any optional QA variables that were not part of bootstrap.
4. Run **Deploy staging** from the exact green `main` SHA.
5. The workflow builds immutable web/worker GHCR images, deploys the Cloudflare media gateway, writes the direct PostgreSQL/Better Auth runtime environment, uses temporary per-operation runner SSH access, applies migrations, deploys transactionally, captures source-to-running-artifact identity, takes backups and performs the restore drill.
6. **Staging certification** runs for the successful deployment SHA.
7. Mandatory Playwright/runtime areas run against the real customer site/Auth/API and produce retained sanitized evidence.
8. For a release containing payment-service wallet subscriptions, configure the payment-service staging values above and dispatch **Payment service staging preflight** with the exact deployed release SHA and deployment run ID. The workflow proves the running release identity before changing runtime configuration.
9. The payment-service preflight verifies authenticated BFF access, authoritative monthly/yearly plans, wallet/status/payment boundaries, JazzCash hosted-portal handoff, invalid-signature rejection and representative mobile Premium UI, then restores ordinary mock staging. Missing required payment-service configuration is explicitly `BLOCKED`; a reproducible integration defect is `FAILED`.
10. Full payment UAT remains a separate evidence step when the provider supplies a supported sandbox/test-wallet flow capable of completing JazzCash wallet linking without real money. It must cover wallet completion, automatic first trial/subscription, paid activation, payment history, cancel, unlink, failure/past-due, duplicate webhook handling and monthly/yearly behavior.
11. Missing required infrastructure/fixtures is `BLOCKED`; reproducible product defects are `FAILED`.
12. Visual differences require explicit human review tied to the exact release SHA.
13. Only `READY FOR UAT` permits human UAT.
14. Production remains a separate explicit approval and must promote the exact tested immutable artifacts; it must not rebuild an untested release.

## Current external blocker boundary

Repository-owned secrets, SSH keys, firewall handoff variables, GHCR deployment credentials and a persistent SSH CIDR no longer need to be manually constructed. Live general staging still depends on the account-owned infrastructure/SMTP/AI inputs required by the ordinary staging contract.

For payment-service wallet subscriptions specifically, repository implementation and the exact-SHA staging preflight are prepared. Full payment evidence cannot be truthfully completed unless the protected staging environment contains the real staging payment-service URL/API key/webhook secret/product return configuration plus a dedicated test MSISDN and a provider-supported JazzCash sandbox/test-wallet mechanism that completes the hosted flow without production money. Missing any mandatory payment input is `BLOCKED`, never PASS.

Production live charging remains separate from staging preflight/UAT and requires explicit production approval plus verified live provider credentials.

## Production handoff prepared in advance

Before any production approval, retain:

- exact staging-tested Git SHA;
- web/worker GHCR image digests;
- successful staging certification artifact;
- successful payment-service staging preflight artifact;
- successful full payment sandbox/UAT evidence when that flow is required for the release;
- human UAT approval;
- pre-production backup/restore evidence;
- tested rollback reference.

After explicit production approval, deploy only the exact tested artifacts to the owner-controlled production server, run non-destructive smoke/health checks, keep rollback immediately available, and retire any prior production environment only after the new environment is verified healthy.
